# 需求文档 → 开发计划

将需求文档分析转化为结构化的开发计划，每项计划仅包含**标题**和**验收标准**，按合理的逻辑顺序排列。

## 工作流程

### 第一步：读取需求文档

用户提供文件路径后，使用 Read 工具读取文件内容。支持常见文档格式：
- Markdown（.md）
- 纯文本（.txt）
- Word 文档（.docx）—— 如遇乱码，提示用户转换为 md 或 txt

如果文件不存在或无法读取，直接告知用户并请求提供正确的路径。

**处理文档中的图片**：按文档从上到下的顺序阅读，每遇到一张图片时：

1. 停下来，告知用户在此处发现图片，并引用图片前后的上下文内容
2. 请用户提供该图片的描述（功能示意、交互流程、界面草图等）
3. 用户提供描述后，将该描述作为该位置需求的补充说明，继续往下阅读
4. 重复上述步骤，直到文档中所有图片处理完毕

### 第二步：初步分析，识别待确认点

通读全文后，整理出以下信息：
1. **核心功能列表** —— 文档中明确提到的所有功能点
2. **模糊/歧义点** —— 以下情况视为待确认：
   - 同一概念有多种解读方式
   - 缺少关键细节（如：数据来源不明确、交互方式未描述、边界条件未定义）
   - 两处描述存在矛盾
   - 技术术语或业务术语含义不清
   - 未指定优先级或范围界限

将模糊点按重要程度排序（影响核心流程的优先），准备逐个提问。

### 第三步：逐个提问澄清

一次只提一个问题，等待用户回复后再提下一个。每个问题应：

- **明确指出**文档中哪段内容引发了疑问（引用原文或指明位置）
- **列出所有可能的解读**，供用户选择或参考
- 如果涉及核心决策，说明不同选择对后续计划的影响

用户回复确认后，将结论记录（可记入 memory），再继续下一个问题。重复直到所有疑问澄清完毕。

**如果在分析中没有发现任何模糊点**（极为罕见），直接进入第四步，但需要在输出中注明"未发现需要澄清的内容"。

### 第四步：生成开发计划

根据需求文档和用户确认的结论，按以下规则输出开发计划。

计划顶部先输出整体验收标准：

1. 根据需求内容提炼一个**具体功能名称**
2. 提取**飞书链接**（若无则向用户询问）
3. **产品验收标准**：用一行自然语言概括主流程，用 `→` 串联关键步骤（如"可完整走通上传视频 → 解析 → 生成动作 → 命名保存 → 积木块可加载"）
4. **[0/N]**：N = 下方 `***** TODO` 子计划总数
5. **注意：** 行仅在需求文档中有额外约束/备注时才添加，否则省略

## 输出格式

```org
**** TODO <具体功能名称>，飞书需求: <飞书链接> [0/N]
     产品验收标准：<一行概括主流程，→ 串联关键步骤>
     注意：<补充约束或说明，不存在则省略此行>

***** TODO [标题]
      - [可验证的条件 1]
      - [可验证的条件 2]

***** TODO [标题]
      - [可验证的条件 1]

***** TODO [标题]
      - [可验证的条件 1]
```

## 输出规则

### 标题
- 直接描述要完成的**功能名称**，简洁清晰（如"子窗口顶部栏"、"视频上传"、"套餐与交易明细完整联调"）
- 测试类计划使用明确的测试类型前缀，如"功能测试——"、"接口联调测试——"、"端到端测试——"，不得使用笼统的"开发者测试——"

### 验收标准
- 每条标准必须是**可验证的、具体的**，不能是模糊描述
- 常用描述模式（不限于此）：
  - **操作驱动**：`点击X → 出现Y`、`可拖拽X到Y`
  - **状态驱动**：`X时，显示Y`、`X后，进入Y状态`
  - **边界条件**：`X为0时，点击Y弹窗"Z"`、`格式/大小不符时显示提示`
  - **端到端链路**：`选X → 点Y → 上传 → 状态更新 → 成功`
- 每条标准独立可测，不需要额外解释
- 只写验收条件，不写实现方法

坏例（太模糊）：
- "登录功能正常" ← 什么叫正常？无法验证
- "套餐展示正确" ← 什么叫正确？

好例（可验证）：
- "登录后窗口顶部依次显示：用户名 / 剩余次数 / 「退出登录」按钮"
- "点击「视频解析」将视频上传至云端，解析成功进入可生成状态"
- "视频解析次数为 0 时，点击「视频解析」弹窗「需要充值后才能使用」"
- "关闭窗口时若已解析未生成，弹确认弹窗「确定要离开吗？」"

### 关联性
- 计划按自然执行顺序排列（UI 组件 → 交互逻辑 → 核心流程 → 完整联调），形成清晰的**从基础到完整**的构建路径
- 相邻子计划之间应有承接关系
- **最后一个计划必定是当前功能的完整联调**，串联所有子计划的验收标准，确保端到端流程可走通

## 补充规则

- **优先独立可测**：每个子计划应能独立开发和验证，减少跨计划耦合
- **不做过细拆分**：验收标准少于 3 条时检查是否可合并到相邻计划（例外：独立性强的边界场景可保留，如"配额不足提示"）
- **不做过粗合并**：验收标准超过 6 条时考虑是否应拆分为独立计划
- **不添加需求文档中没有的功能**：只输出文档中明确要求或合理推断出的内容。如果推断的内容不确定，回归第三步提问确认
