# 全局审查（Global Review）

## 目标

回答：**这次变化合入项目后，整个代码库是否出现了结构性问题？**

Global Review 不是第二遍 diff review，而是以变化后的仓库状态为对象。

## 检查重点

### 重复资产

寻找语义高度重叠的组件、Hook/Composable、工具函数、Type/Interface/DTO/Schema/Model、Service/UseCase、业务逻辑、API/Client、验证/缓存/日志/格式化能力。

组件比较 Props、状态、UI 结构、事件处理、数据获取和业务职责；工具函数比较输入、输出和行为；业务逻辑即使实现不同，也要判断是否表达相同领域规则。

### 架构

检查模块边界、依赖方向、循环依赖、跨层访问、重复抽象、职责泄漏、过度耦合和架构漂移。

### 依赖碎片化

识别多个库或机制承担相同职责，例如多个 HTTP Client、状态管理、日期、校验或日志方案。

### Dead / obsolete code

检查变化导致的孤儿代码、无用导出、旧实现、废弃兼容层和不可达代码。

## 证据

每个重复或架构问题至少给出两个相关位置及其关系。不确定时标记“建议人工确认”，不要强行判定。

## 原则

优先复用已有资产或合并抽象，而不是继续创建等价实现。相似但职责合理的代码不应被强行合并。

## 输出

阻断问题、高风险结构问题、重复/可合并资产、架构建议、非阻断建议，以及是否允许进入 Commit Gate。
