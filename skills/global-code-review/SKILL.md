# Global Code Review

> 默认使用中文。代码、API、错误信息、命令和原始标识符保持原文。

## 适用范围

用户要求评估一次提交或一组变更对整个项目的影响、提交/MR 前做跨模块审查，或 Change Review 发现需要扩大范围时使用。

不适用于：

- 只审查变更本身的 Bug、安全和测试：使用 change-code-review；
- 没有具体变更、要求长期技术债或项目健康基线：使用 deep-code-review。

## 工作流

1. 读取[共享审查协议](../../code-review-rules/review-protocol.md)。
2. 确认变更的 Base、Target、分支、变更文件和 Change Review 已知结论；没有具体变更目标时不要自行创建一个“全项目 Global Review”。
3. 加载仓库根目录的 Universal、Language、Framework 和项目规则，记录版本、禁用项、缺失项和范围限制。
4. 建立变更影响地图，按以下顺序检查：
   - 导出 API、入口、调用方和被调用方；
   - 组件、Hook、Composable、工具、Service、UseCase、DTO、Schema、Model；
   - API/Client、IPC/Preload/Window 能力、配置和依赖；
   - 模块边界、循环依赖、跨层调用和技术栈碎片化。
5. 从变更涉及的资产开始语义搜索已有实现。认定重复时至少提供两个位置、职责关系和实际影响；名称相似或文本相似本身不够。
6. 判断变更是否引入架构退化：新增边界穿透、重复基础能力、依赖方向反转、共享类型分叉或无法维护的耦合。
7. 只在证据需要时扩大扫描；默认排除第三方目录、构建产物、缓存和生成文件，并记录排除项。
8. 执行项目实际存在且与结论相关的验证，例如类型检查、构建、依赖分析或测试；未执行内容按共享协议标记。
9. 使用[报告模板](../../code-review-rules/review-report.md)输出受影响资产、重复/架构 Findings、证据、验证结果和最终结论。

## 重点约束

- 不重复输出 Change Review 已确认的局部问题；本 skill 关注跨资产影响。
- 重复 Finding 必须有至少两个位置和语义证据。
- 架构问题必须说明违反的边界、依赖路径或维护影响，不以个人设计偏好阻塞合并。
- 发现需要周期性基线、技术债趋势或全项目治理时，建议转交 deep-code-review。
- Review 默认只读，不切换分支、不修改代码、不提交、不推送、不自动安装依赖。
