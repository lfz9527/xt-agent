# Deep Code Review

> 默认使用中文。代码、API、错误信息、命令和原始标识符保持原文。

## 适用范围

用户要求周期性治理、重大版本发布前、架构重构后、事故复盘后的全面审查，或明确要求建立项目健康基线时使用。

单次提交、工作区 diff 或 MR 的问题审查使用 change-code-review；变更对已有资产的影响审查使用 global-code-review。

## 工作流

1. 读取[共享审查协议](../../code-review-rules/review-protocol.md)。
2. 先声明审查边界、时间预算、排除项、语言/框架/Runtime、构建系统、测试能力和可用历史报告。大型仓库按风险区域分批，不承诺无边界扫描。
3. 建立项目资产地图：入口、模块、API、领域能力、UI、数据访问、配置、依赖、测试和安全边界。
4. 建立模块/依赖关系，检查循环依赖、跨层调用、技术栈碎片化、重复能力和关键模块复杂度；对核心路径优先使用实际导入、配置和构建证据。
5. 评估测试薄弱区域、安全边界、高风险基础设施、死代码/废弃代码和缺失的共享治理能力。没有引用、调用链或工具结果时降低结论强度。
6. 若存在同口径历史报告，比较资产、Findings、重复能力、架构风险和技术债指标；没有可定位基线时明确写“无可比基线”，不得编造趋势。
7. 对高风险观察建立统一 Finding，对低置信度观察放入“需人工确认”，并给出影响、证据、置信度和可执行治理动作。
8. 执行项目实际存在且与关键结论相关的测试、静态分析、类型检查、构建或依赖分析；未执行内容按共享协议标记。
9. 使用[报告模板](../../code-review-rules/review-report.md)输出扫描范围、资产与架构观察、趋势/基线限制、治理行动项、Findings、验证结果和最终结论。

## 重点约束

- 默认排除第三方目录、构建产物、缓存、生成文件和无法解释的二进制文件。
- 不把一次 grep 命中、文件数量或主观复杂度判断直接当成全局结论。
- 死代码、重复能力、技术债和架构漂移都要提供引用、调用关系、工具输出或历史对比证据。
- Deep Review 是基线和治理报告，不自动修改代码、创建重构分支、提交或推送。
