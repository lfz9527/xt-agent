# MR 描述

## 生成原则

- 先确认 MR 的目标分支、范围和用户是否要求描述文本还是实际创建 MR。只要求文本时只输出文本，不调用外部平台。
- 根据用户明确意图和实际 diff 判断类型；标题前缀是线索，不是唯一依据。混合变更选择一个主要目的，并在影响范围中说明其他部分。
- 使用整个 MR 的目标分支差异生成整体描述。只有用户明确要求“当前用户提交报告”时，才使用 `--author` 过滤；不能一边过滤提交、一边使用包含所有协作者的 diff 却声称只描述当前用户。
- `Closes` 只使用用户或需求上下文明确提供的 Issue 号/链接；分支名中的数字只能作为待确认线索，不能自动当作 Issue。

### 输出语言（强制）

- MR 标题（如同时生成）、字段名、章节标题、问题说明、方案说明、影响范围和验证结果必须使用中文；英文输入材料先翻译后输出。
- `Closes` 等平台关键字、Issue/commit 标识、文件名、函数名、API、错误码、命令、URL 和代码片段保留原文，避免破坏平台语义或技术准确性。
- 只有用户明确指定其他语言，或仓库已验证存在更高优先级的语言规范时，才改变中文默认值。

## 类型字段

按实际类型选择对应字段：

```text
修复类：类型、问题现象、问题原因、修复方案、引入来源、责任人
功能类：类型、需求目标、需求原因、实现方案、Closes（已知时）
重构类：类型、重构目标、重构原因、重构方案、影响范围
性能类：类型、优化目标、优化原因、优化方案、验证结果
工程维护类：类型、变更内容、变更原因、影响范围
```

字段应有真实内容。若来源或责任人无法确认，写明“未定位/未确认”、已执行的检查和当前判断；禁止伪造 commit hash、作者或性能对比。

## 来源提交与责任人

可按需组合使用以下检查：

```text
git log -S '<symbol>' -- <file>
git log -G '<pattern>' -- <file>
git log --follow -- <file>
git blame <file> -L <start>,<end>
git merge-base --is-ancestor <source-commit> <target-ref>
git show -s --format='%an <%ae>' <source-commit>
```

只有 `git merge-base --is-ancestor` 成功时，才可把来源提交描述为已进入目标分支。若问题由当前 MR 引入，明确写“问题在当前 MR 内部引入并修复”，不要把当前 MR 的提交伪装成历史来源。

## 生成后检查

- 每个必需字段都有内容或有明确的未确认说明。
- 描述中的文件、模块、数据和验证结果都能从需求、提交记录或 diff 找到依据。
- 不把“历史遗留”“未知”“初版对接”当作没有证据时的唯一结论。
