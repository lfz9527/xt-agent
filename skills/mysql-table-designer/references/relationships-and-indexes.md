# MySQL 关系、约束与索引决策

设计多表关系、关联表、外键、历史快照、软删除唯一性或联合索引时读取本文件。

## 规范化与有意冗余

- 默认将可独立维护、具有自身身份或被多处引用的数据建为独立实体表。
- 多值属性在需要单独查询、约束或维护时拆成明细表或关联表；一个业务上作为整体处理的地址、名称或描述不因“文字可拆分”就自动违反 1NF。
- 联合主键表的普通属性应依赖完整关系。只依赖其中一方的当前属性通常属于对应实体表。
- 以下情况可以有意冗余：订单和收货地址快照、审计记录、事件载荷、经证实的读性能需求、跨服务边界的数据副本。
- 每个冗余字段都应说明来源、写入时机、是否允许与源数据不同，以及由谁保证一致性。快照字段应使用能表达历史语义的名称或注释。

## 关系建模

- 一对一：在从表外键上增加唯一约束；根据可选性决定外键是否允许 `NULL`。
- 一对多：外键放在“多”的一侧，并按常见父记录查询路径评估索引。
- 多对多：使用关联表。纯关系可使用联合主键；若关联记录需要被其他表引用、独立生命周期或多次历史记录，可用代理主键，同时增加真正的业务唯一约束。
- 关联表的时间、状态、角色、排序等字段只有在描述该关系时才保留；快照或审计字段例外，但需明确说明。

## 外键与删除策略

- 同一数据库内且需要数据库保证引用完整性时，优先使用命名外键约束。
- 跨服务、跨库、分片、在线迁移或已有团队规范禁止外键时，可以只保留类型一致的关联字段和索引，但必须说明完整性由哪个应用流程保证。
- 不以“高并发”单独作为取消外键的理由；结合写入量、锁与迁移影响、故障修复成本及孤儿数据风险决定。
- 父记录通常不能随意删除时使用默认限制行为或 `RESTRICT`；子记录完全从属于父记录且允许物理删除时才用 `CASCADE`。
- 使用 `SET NULL` 前确认关系可选且列允许 `NULL`。软删除体系通常不依赖物理删除级联，应明确查询过滤和恢复语义。
- MySQL 要求外键列和被引用列具有可用索引。显式索引与联合查询索引可复用时，不要再创建重复单列索引。

## 查询驱动的索引

先列出关键查询的过滤、连接、排序、分组和返回规模，再设计索引。

- 唯一索引用于真实业务唯一性，不只是性能优化。
- 联合索引通常先放稳定的等值过滤/连接列，再考虑范围和排序列；以实际查询和执行计划验证，不机械套用顺序。
- 利用最左前缀判断索引是否可复用，删除被更长索引完全覆盖且没有独立价值的前缀索引。
- 单独为低选择性的状态或布尔列建索引通常价值有限；它们与租户、用户、时间等条件组合时才可能有效。
- 避免为每个字段自动建索引。索引会增加存储以及 INSERT、UPDATE、DELETE 成本。
- 长 `VARCHAR`、`TEXT` 和 `utf8mb4` 联合索引要检查索引键长度；不要为了通过长度限制随意使用会破坏唯一性的前缀索引。
- 表规模、冷热分布或查询信息不足时，标记候选索引及其对应查询，不伪装成已经验证的性能结论。

## 软删除与唯一性

- MySQL 唯一索引允许多个 `NULL`。直接使用 `UNIQUE(email, deleted_at)` 通常不能保证“仅活动记录 email 唯一”，因为所有活动记录的 `deleted_at` 都是 `NULL`。
- 如果业务要求删除后复用唯一值，可在兼容版本中使用生成列：活动记录映射到规范化业务值，已删除记录映射为 `NULL`，再对生成列建立唯一索引。
- 其他可行方案包括把活动身份拆到独立表，或在删除时迁移/改写唯一值。选择必须匹配恢复、重复删除、审计和并发语义。

## 多表输出检查

- 被引用表应先创建；循环引用优先重新检查关系是否必要。
- 每个外键的类型、signedness、字符集和 collation 与被引用列兼容。
- 每个关系的基数、可选性和删除动作与字段 `NULL` 属性一致。
- 订单明细等历史表不应仅通过当前商品表恢复过去的名称、单价或税率；需要历史事实时保留并标注快照字段。
