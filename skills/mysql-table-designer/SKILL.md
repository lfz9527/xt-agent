# MySQL 表结构设计

将业务需求转换为可执行、可解释的 MySQL 表结构设计。只生成设计和 DDL，不连接数据库、不执行 SQL，也不修改用户现有数据库。

## 工作方式

1. 从需求中提取实体、字段、关系、唯一性、数据生命周期、预计规模和主要读写路径。
2. 识别会影响正确性的缺失信息。只有主键身份、唯一性、金额精度、删除策略、关系基数或版本兼容等无法安全假设时，才提出精简问题；其余缺口使用明确假设继续设计。
3. 先确定数据模型和约束，再根据实际查询设计索引，最后生成 DDL。
4. 输出前完成一致性检查，不用默认值、冗余字段或应用层兜底掩盖未解决的业务问题。

用户未指定环境时，声明按 MySQL 8.0+、InnoDB、`utf8mb4` 设计。不要使用仅在更高版本可用的语法而不说明兼容范围。

## 核心决策规则

- 优先遵循项目现有命名、主键、审计字段、字符集和迁移约定；没有项目约定时使用一致的小写蛇形命名。
- 为每张表选择稳定且尽量短的主键。实体表可使用与规模匹配的自增整数；纯关联表可使用联合主键，或使用代理主键并对业务键增加唯一约束。不要统一强制 `BIGINT AUTO_INCREMENT`。
- 外键列的数据类型、长度和有无符号属性必须与被引用列一致。
- `NULL` 表示值确实可以缺失；`NOT NULL` 表示插入时必须给出有效值。只有存在真实业务默认语义时才添加 `DEFAULT`，不得用 `''`、`0` 或虚假枚举值替代必填输入。
- 金额和其他精确小数使用按范围与小数位确定的 `DECIMAL(p,s)`；不要把 `DECIMAL(18,2)` 套用于所有业务，也不要用浮点数保存必须精确的金额。
- `DATETIME` 与 `TIMESTAMP` 根据时间范围、时区转换和系统存储策略选择。审计字段由数据库还是应用维护应保持一致，不默认添加软删除或自动更新时间字段。
- 状态值、布尔值和枚举必须来自需求或明确假设；版本支持时可用命名 `CHECK` 约束保证已确认的取值或范围。
- 默认按 3NF 组织可独立维护的数据，但允许为历史快照、审计、性能或服务边界保留有意冗余；必须说明来源、用途和一致性策略。地址等复合业务值不能仅因“可拆分”就强制拆表。
- 索引必须对应唯一性、外键维护或已知查询条件。按过滤、连接、排序和范围条件决定联合索引顺序，避免重复索引和没有访问依据的低选择性单列索引。
- 是否创建数据库外键取决于同库边界、引用完整性、分片与运维约束，而不是仅以“高并发”为理由省略。`ON DELETE SET NULL` 的列必须允许 `NULL`；级联删除必须符合实体生命周期。
- 密码字段保存盐化密码哈希，命名为 `password_hash` 等明确名称，不设置空默认值。身份证号等敏感数据不能仅靠字段注释宣称“已加密”。
- 字符集默认使用 `utf8mb4`；排序规则根据 MySQL 版本及大小写、重音、语言和唯一比较语义选择，不固定为某一种 collation。

- 当设计多表关系、关联表、外键、历史快照、软删除唯一性或联合索引时，读取 [references/relationships-and-indexes.md](references/relationships-and-indexes.md)。

## 输出要求

遵循用户指定的输出形式。用户没有指定时，按以下顺序输出：

1. **设计假设**：仅列出会影响 DDL 的版本、规模、时区、唯一性或生命周期假设；没有则省略。
2. **表与关系概览**：简要说明每张表的职责、主键和关系。
3. **DDL**：按依赖顺序给出完整语句。
4. **设计说明**：解释非显然的索引、外键、冗余和兼容性选择，并列出仍需业务确认的事项。

DDL 必须满足：

- 每条语句以分号结尾，表定义完整且没有 `...`、`TODO` 等占位符。
- 默认不包含 `DROP TABLE` 或 `CREATE TABLE IF NOT EXISTS`，除非用户明确要求。
- 字段明确类型、`NULL`/`NOT NULL`、必要的默认值和中文 `COMMENT`；表包含中文 `COMMENT`。
- 默认使用 `ENGINE=InnoDB` 和 `utf8mb4`，排序规则与兼容目标一致。
- 主键、唯一约束、普通索引、外键和 `CHECK` 约束使用稳定且不冲突的名称。
- 多表 DDL 按被引用表在前的顺序输出；只有循环依赖无法通过建模消除时，才在建表后用 `ALTER TABLE` 添加外键并说明原因。
- 如果用户只要求 DDL，将假设和关键取舍写成简短 SQL 注释，不额外展开说明。

## 输出前检查

- 每个必填字段是否真的要求调用方提供，而不是被无意义默认值掩盖？
- 可选唯一字段是否正确区分 `NULL` 与空字符串？
- 主键和整数类型是否匹配预计规模，所有外键类型是否完全一致？
- 关联表是否防止重复关系，附加字段是否依赖该关系或被明确标记为快照？
- `SET NULL`、`CASCADE`、软删除和唯一约束是否能同时满足生命周期规则？
- 每个索引是否对应具体查询或完整性需求，是否存在重复或前缀冗余？
- DDL 是否只使用目标 MySQL 版本真正支持并执行的特性？
- 密码、令牌和个人敏感数据是否使用正确的存储语义且没有危险默认值？
