# P2-3.3 Checkpoint / 崩溃恢复

> P2-3.3 让 Loop 在 Agent / Tool 执行完成、状态迁移尚未完成时发生进程崩溃后，可以从 `.loop` 持久化 checkpoint 恢复，而不是重复执行外部副作用。

## 恢复模型

```text
Stage Executor
     ↓
Stage Result
     ↓
Runtime Facts 持久化
     ↓
Checkpoint 原子落盘
     ↓
Kernel Transition
     ↓
Checkpoint 清理
```

如果进程在 checkpoint 与 Transition 之间退出：

```text
新进程
  ↓
读取 Run State
  ↓
读取当前 Stage Checkpoint
  ↓
校验输入 Fingerprint
  ↓
恢复 Facts
  ↓
Kernel Transition
  ↓
清理 Checkpoint
```

因此 Agent / Tool 不会因为 Runtime 在中间崩溃而被无条件重复调用。

## 持久化位置

- Runtime State：`.loop/runtime/runs/<run-id>/state.yaml`
- Execution Checkpoint：`.loop/runtime/runs/<run-id>/checkpoint.json`
- Mutation Journal：`.loop/runtime/runs/<run-id>/mutation-journal.jsonl`

## 安全约束

1. Checkpoint 必须绑定 `runId`。
2. Checkpoint 必须绑定 Stage。
3. Checkpoint 保存输入 Fingerprint；恢复时不匹配直接 `[LOOP_BLOCKED]`。
4. Checkpoint 使用临时文件 + `rename` 原子替换。
5. 恢复后的状态迁移仍必须经过 Kernel Transition Guard。
6. Checkpoint 不是项目级 Lock，也不能替代 Resource Lock。
7. 正常 Transition 成功后立即清理 checkpoint。

## 测试要求

- 新 Runtime 实例能够读取旧实例留下的 checkpoint。
- 恢复 checkpoint 时不再次调用 Agent / Tool。
- checkpoint 与 Runtime State 不一致时必须阻断。
- 正常执行完成后 checkpoint 必须被清理。
