# P2-5 Run Audit & Replayability

P2-5 makes Runtime history useful for diagnosis and recovery instead of treating audit output as plain logging.

## Goals

- Every Runtime audit record remains associated with a single `runId` and `policyRevision`.
- A Run can be reconstructed from its persisted state-transition events without executing the Agent again.
- Cross-run records are ignored during replay, preventing unrelated Runs from contaminating a timeline.
- Malformed audit records and broken transition chains fail closed with `[LOOP_BLOCKED]`.
- Replay is observational: it never mutates Runtime state, executes tools, or re-runs Agent work.
- The derived replay report is persisted as a Run-scoped file for inspection and downstream tooling.

## Artifacts

Runtime audit history is stored at:

```text
.loop/runtime/history.jsonl
```

Run-scoped mutation history remains at:

```text
.loop/runtime/runs/<run-id>/mutation-journal.jsonl
```

The materialized P2-5 replay report is stored at:

```text
.loop/runtime/runs/<run-id>/replay-report.json
```

`history.jsonl` is the authoritative source of truth. `replay-report.json` is a derived, human/machine-readable artifact and must never be used to reconstruct Runtime state in place of the audit history.

## Replay model

```text
history.jsonl
     ↓
parse + validate
     ↓
filter runId
     ↓
STATE_TRANSITION events
     ↓
validate from → to chain
     ↓
ReplayResult
     ↓
ReplayReport
     ↓
.loop/runtime/runs/<run-id>/replay-report.json
```

`RuntimeAuditReplay` exposes:

- `read(runId)` — validated audit events belonging to the requested Run.
- `replay(runId)` — transition timeline, final status, and policy revisions observed by that Run.

`RuntimeReplayReport` materializes the replay result into a stable ordered timeline with event summaries and counts. `RuntimeReplayReportStore` persists and reads that report under the Run directory.

## Persistence contract

- The parent Run directory is created automatically when the report is written.
- Report writes use a temporary file followed by rename so readers do not observe a partially written JSON document.
- `runId` is validated before it is used as a filesystem path; traversal such as `../escape` is blocked.
- A missing report is a valid absence and returns `undefined` when read.
- Malformed persisted JSON fails closed with `[LOOP_BLOCKED]`.
- Persisting the report does not mutate Runtime State or execute any Agent/tool side effect.

## Invariants

1. Empty history is a valid replay with no reconstructed status.
2. Invalid JSON is blocked; it is never silently skipped.
3. Missing event identity, timestamp, policy revision, or payload is blocked.
4. A transition whose `from` does not equal the previously reconstructed status is blocked.
5. Events from another Run are excluded from the requested replay.
6. Replay performs no Runtime mutation and does not invoke an Executor.
7. `replay-report.json` is derived data; `history.jsonl` remains authoritative.

## Boundary

P2-5 does **not** attempt to replay arbitrary Agent/tool side effects. It reconstructs the Runtime's authoritative observable timeline. Actual resource changes are represented separately by the mutation journal and Git/worktree consistency mechanisms.

This keeps replay deterministic and safe while leaving full side-effect replay for a later Runtime capability.
