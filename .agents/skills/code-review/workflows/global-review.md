# 全局审查（Global Review）

## 目标

回答：**这次变化合入项目后，整个代码库是否出现了结构性问题？**

Global Review 不是重新审查 diff，而是以变化后的仓库状态为对象，从项目全局寻找重复、碎片化、架构退化和资产复用问题。

## 重点检查

### 1. 组件重复

寻找功能、UI、交互和职责高度重叠的组件。比较：

- Props / 参数
- 状态
- UI 结构
- 事件处理
- 数据获取
- 业务职责

发现重复时，优先建议复用已有组件或抽取共享组件。

### 2. 工具函数重复

寻找名称不同但语义相同、或者实现高度相似的工具函数，包括日期、金额、字符串、数组、对象、请求、校验、转换等。

不要只比较函数名或文本，应判断输入、输出和行为。

### 3. 业务逻辑重复

识别跨 Service、Controller、Hook、UseCase、Domain 等位置重复出现的业务规则。即使代码实现不同，只要表达相同领域规则，也应提示潜在重复。

### 4. 类型和模型重复

检查重复的 Interface、Type、DTO、Schema、Entity、Model，以及只存在细微差异的类型定义。

### 5. API 和能力重复

检查重复 Endpoint、API Client、数据访问入口、缓存、日志、验证、格式化等能力。

### 6. 依赖碎片化

检查多个库/机制是否承担相同职责，例如多个 HTTP Client、日期库、状态管理、校验库、日志库。

### 7. 架构退化

检查模块边界、依赖方向、循环依赖、跨层访问、重复抽象、职责泄漏和项目既有架构规则违反。

### 8. Dead / Obsolete Code

检查新变化导致的孤儿代码、无用导出、旧实现、废弃兼容层和不可达代码。

## 证据要求

每个重复或架构问题至少给出两个相关位置及其关系，例如：

```text
现有资产：src/shared/utils/date.ts:20
新实现：src/order/utils/date.ts:12
关系：两者都实现 UTC 时间格式化，仅参数命名不同
```

不确定时标记为“建议人工确认”，不要强行判定为问题。

## 输出

按以下类别输出：

- 阻断问题
- 高风险结构问题
- 重复/可合并资产
- 架构改进建议
- 非阻断建议

最终给出是否允许进入 Commit Gate 的结论。
