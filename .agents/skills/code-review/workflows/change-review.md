# 变化审查（Change Review）

## 目标

回答：**这次代码变化本身是否正确、安全、可测试，并且没有明显回归？**

## 流程

1. 获取当前工作树或 PR/MR 的变更范围。
2. 读取项目规则和相关配置。
3. 识别语言、运行时、框架、测试框架。
4. 从 diff 进入受影响的函数、类、模块、调用方和被调用方。
5. 只加载与当前变化相关的规则。
6. 分析并验证发现的问题。
7. 输出按严重程度排序的 Review。

## 检查重点

- 逻辑正确性和边界条件
- 空值、错误和异常处理
- 异步、并发、资源生命周期
- 认证、授权和输入校验
- API 兼容性
- 数据一致性、事务和幂等性
- 性能回归
- 测试覆盖和回归风险
- 项目既有编码/架构规则

## 范围扩展原则

默认只审查变化及直接影响范围。只有当一个问题需要上下文证明时，才继续读取相关调用链或依赖。

不要因为“可以这样写得更漂亮”而产生阻断性 Review。
